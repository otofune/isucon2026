# isucon-impl

Claude がリードとしてスコープ、設計、統合、確認、報告に責任を持ち、調査、実装、レビューを Codex CLI に委譲する。委譲先は Claude の subagent ではなく Codex にする。

確認はベンチマークで行う。セルフのテストコードの追加や、ブラウザでの QA は行わない。

## 開始前の確認

ファイルを編集する前に、次の2点をユーザーに聞く。依頼文で指定済みの項目は聞かない。

1. 実装漏れチェックの回数
   - 0: 行わない
   - 1: 初回の実装後に1回行う
   - 2: 1回行って修正し、もう1回行う
2. レビュー・修正ループの上限
   - レビューしない
   - 3回
   - 5回
   - 10回

回答を受けたら、次の内容を短く示してから実装を始める。

1. 依頼された動作や改善の理解
2. 対象のファイルやサブシステム
3. リードが自分で進める作業
4. 委譲する作業と、書き込み範囲が重ならない理由
5. 反映先の台と、比較の基準にするスコア

## 役割

リードの責任は次のとおり。

- `docs/regulation.txt`、`docs/manual.md`、`AGENTS.md`、対象のコードを読み、作業を定義する。
- 他の作業を止めている作業は自分で進める。
- 並列に進められる作業だけを委譲し、書き込み範囲を重ねない。
- 委譲の結果を確認してから統合する。
- 重複を取り除き、変更全体の整合を取る。
- 反映、ベンチマーク、報告を行う。

Codex の責任は次のとおり。

- 1つの調査、範囲を限った1つの実装、1つのリスク確認だけを行う。
- 指定された範囲だけを変更する。
- 変更したファイル、実行したコマンド、失敗、未解決の点を返す。
- 大きなリファクタリングや無関係な整理を行わない。

## Codex の実行

`codex exec` をリポジトリのルートで、Bash の `run_in_background` で実行する。完了すると通知が来るので、途中でポーリングしない。並列に進めるときは、複数の Bash を同じ応答で起動する。

指示はスクラッチパッドのファイルに書いて標準入力から渡し、最終回答は `-o` で受け取る。出力先は委譲ごとに分ける。

```sh
codex exec --dangerously-bypass-approvals-and-sandbox -o <スクラッチパッド>/<名前>.txt - < <スクラッチパッド>/<名前>.prompt
```

調査、実装、実装漏れチェックのどれも、この形で実行する。モデルと推論強度は `~/.codex/config.toml` の設定を使う。

SSH、反映、ベンチマーク、git の commit と push はリードが行う。サンドボックスを外した Codex は技術的には実行できるので、指示に禁止事項として必ず書く。

## 委譲のひな形

### 調査

```text
<repo/path> で <具体的な問い> を調べる。ファイルは編集しない。git の commit と push、SSH、反映、ベンチマークは行わない。次を返す。
- 関連するファイルと行番号
- 確認した動作
- 実装上の制約
- 推奨する変更の形
- 実行したコマンド
```

### 実装

```text
<repo/path> に <範囲を限った作業> を実装する。
書き込み範囲: <ファイルまたはディレクトリ>
<他の作業の範囲> には触れない。
既存の書き方に従う。テストコードは追加しない。git の commit と push、SSH、反映、ベンチマークは行わない。次を返す。
- 変更したファイル
- 実装した動作
- 実行した確認コマンドと結果
- リードが統合するときの注意点
```

### 実装漏れチェック

```text
現在の作業ツリーを、依頼された動作 <依頼または計画> と照らして確認する。
この範囲で具体的な実装漏れがあれば、ファイルを編集して直す。
無関係なファイルには触れず、設計を広げない。git の commit と push、SSH、反映、ベンチマークは行わない。次を返す。
- 変更したファイル
- 残る指摘（重大な順に、ファイルと行番号付きで）
- 実行した確認コマンドと結果
- 統合時のリスク
```

## レビュー・修正ループ

小さくない差分は `codex exec review` でレビューし、対応が必要な指摘がなくなるか、上限に達するまで修正を繰り返す。これも `run_in_background` で実行する。

```sh
# commit 前: 作業ツリーに無関係な変更がないときに使う
codex exec review --uncommitted -o <スクラッチパッド>/review-<回数>.txt

# commit 後: 無関係な未コミットの変更があるときはこちらを使う
codex exec review --commit <SHA> -o <スクラッチパッド>/review-<回数>.txt
```

指摘は修正する前に、リードがコードと照らして正しいか確認する。

対応が必要な指摘の例は次のとおり。

- クラッシュ、データ不整合、レースコンディション
- 認可の抜け
- `docs/manual.md` の仕様や API の契約との不一致
- レギュレーション違反
- スコアの低下やベンチマークのエラーにつながる変更

好みだけの指摘、スコープ外のリファクタリング、意図したトレードオフ、コードやベンチマークで否定された指摘は無視してよい。無視した理由は短く記録する。

## 統合

- Codex の変更を取り込む前に、変更されたパスと差分を確認する。
- 書き込み範囲の外が変更されていたら、別の変更として確認してから残すか判断する。
- Codex の変更が重なったら、どちらかをそのまま採用せず、リードが最終形を作る。
- 既存の設計、命名、ヘルパーを優先する。
- 作業ツリーにある無関係な未コミットの変更を戻さず、commit にも含めない。

## 確認

1. Go を変更したら、`webapp/go` で `go build ./...` を実行し、ビルドできることを確かめる。
2. `AGENTS.md` の手順で、commit、push、対象台への反映を行う。共有DBの PostgreSQL を再起動する変更では、全リージョンの接続が一時的に切れることを踏まえて反映の順番を決める。
3. `bench` Skill でベンチマークを実行し、変更前のスコアと比較する。ボトルネックの調査が必要なら計測付きで実行する。
4. スコアが下がった、またはベンチマークがエラーで終わったときは、Conclusion のログと計測結果から原因を調べて直し、もう一度実行する。

## 報告

最後に次の内容を簡潔に報告する。Codex のやり取りは、求められない限り貼らない。

- 変更した内容と場所
- Codex に委譲した作業
- 反映した台と commit
- ベンチマークのジョブ ID、スコア、変更前からの差
- 対応した指摘と、無視した指摘
- 残るリスクや未完了の作業
